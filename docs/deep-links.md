# Deep links — the full list of `kinkane.app` URLs the apps must handle

Every link below is generated by this backend and sent to a real person, in an
email, a push notification or a shared message. On a phone each one should open
the app rather than the mobile web page.

All paths are relative to `APP_URL` (`https://kinkane.app` in production — the
`.app` domain, not `.com`; see [config/index.ts](../src/config/index.ts)).

## One prefix: `/redirect`

Every link meant to open the app is sent as **`APP_URL/redirect/<path>`**, built
by `appLink()` in [lib/app-link.ts](../src/lib/app-link.ts). So the association
files register one pattern — `/redirect/*` — instead of a list that has to be
kept in step with every email template.

- **App installed:** the OS matches `/redirect/*` and hands the URL to the app.
  The app strips `/redirect` and routes on the rest, query string included.
- **No app, or a desktop:** the request reaches `GET /redirect/*` on the API
  (proxied from the web host — see
  [referral-link-routing.md](referral-link-routing.md)), which answers `302` to
  the same path without the prefix, query string intact. `/redirect/r/*` goes to
  the referral handler instead, so the click is still counted.

A path that doesn't start with `/redirect` opens the web page, not the app. It
doesn't fail — it just quietly stops feeling like an app — which is why every
generator goes through `appLink()` rather than `config.appUrl`.

## Must be deep links

| Link as sent | Where it comes from | Notes |
| --- | --- | --- |
| `/redirect` | welcome, follow-request and weekly-digest emails | bare prefix — send it to the app's home tab |
| `/redirect/r/:code` | shared referral links | slug-less form — chat clients clip the last path segment |
| `/redirect/r/:code/:slug` | `buildReferralLink()`, referral invite emails, share sheets | `?c=` share channel rides along and must be forwarded |
| `/redirect/books/:bookId` | new-recommendation email | |
| `/redirect/explore` | subscription-confirmed email | |
| `/redirect/subscribe` | trial-ending email | |
| `/redirect/account/subscription` | payment-failed and cancellation emails, `upgradeUrl` on 402 responses | |
| `/redirect/account/subscription?checkout=success` | Stripe subscription checkout return | |
| `/redirect/account/subscription?checkout=cancelled` | Stripe subscription checkout return | |
| `/redirect/cart?checkout=success&orderId=N` | Stripe order checkout return | default; `STRIPE_ORDER_SUCCESS_URL` overrides it |
| `/redirect/cart?checkout=cancelled&orderId=N` | Stripe order checkout return | |
| `/redirect/reset-password?token=TOKEN` | password-reset email | |
| `/redirect/cancel-email-change?token=TOKEN` | email-change notice to the old address | |

`/invite?ref=CODE&c=CHANNEL&cid=CLICKID` is not sent to anyone: it is where the
server-side referral redirect lands a browser that *didn't* open the app, so it
stays unprefixed. The app should still handle it (see below) in case a reader
taps it again from their history.

The Stripe return URLs are only built this way when `STRIPE_CHECKOUT_*_URL` and
`STRIPE_ORDER_*_URL` are **unset**. An override in the environment wins, and one
without `/redirect` sends the return to the web.

## Old links, still registered

Links sent before the switch have no prefix. Keep these patterns in the
association files alongside `/redirect/*` so those links still open the app:

`/`, `/r/*`, `/invite`, `/books/*`, `/explore`, `/subscribe`,
`/account/subscription`, `/cart`, `/orders`, `/reset-password`,
`/cancel-email-change`

They can come out once nothing sent before the switch is still live. Password
reset and email-change tokens expire within the hour, and Stripe return URLs only
matter mid-checkout. Referral links are the long tail — they sit in chat
histories indefinitely — so `/r/*` is the one worth keeping longest.

## Deliberately *not* deep links

Register these as exclusions, not omissions — a wildcard that swallows them
would be worse than no deep linking at all. None of them is sent with the
`/redirect` prefix.

| Path | Why |
| --- | --- |
| `/unsubscribe?token=TOKEN` | must work for someone who has deleted the app, and often opens in a webmail browser with no app session |
| `/privacy` | email footer, linked for readers who are not users |
| `/terms` | email footer, linked for readers who are not users |
| `/about` | `REFERRAL_VIDEO_URL` default — a public marketing page |

## Things that are easy to get wrong

**Strip the prefix, keep the query.** The app should route on everything after
`/redirect`, with the query string. The Stripe returns carry state there:
`?checkout=success` and `?orderId=` are the only signal the app gets that a
payment completed — the webhook is what actually updates the account, but the
redirect is what tells the UI to stop showing a spinner. A handler that matches
the path and drops the query string will strand the user on a screen that never
resolves.

**Tokens are single-use and short-lived.** `/redirect/reset-password` and
`/redirect/cancel-email-change` links are frequently opened on a different
device from the one the app is installed on. They must keep working in a plain
browser, which is what the server-side forward is for. The forward is sent with
`Cache-Control: no-store` so a CDN can't replay a token.

**Report referral taps by hand.** A `/redirect/r/...` tap that opens the app
makes no HTTP request, so the click is never counted unless the app calls
`POST /api/v1/referrals/clicks` — same as before the prefix.
